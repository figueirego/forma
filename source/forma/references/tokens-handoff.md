# Tokens, documentation and implementation handoff

## Extraction and migration

1. List themes/configurations and representative components. Search values with rg; count use by context, not only textual occurrence.
2. Relate values to roles: primary text, input border, selection, space between groups. Equal values can serve different roles.
3. Record origins, consumers and exceptions. Classify them as preserve, consolidate or replace.
4. Propose semantic aliases, migrate one flow and verify it before propagating within the authorized scope.

The [example JSON](../assets/tokens.example.json) uses a simple custom format and does not claim DTCG or editor-native schema compliance. Adapt it to the existing pipeline; do not replace that pipeline merely to use this example.

For the background/sidebar/panel/controls combination, the [clean interface foundation](clean-shell.md) provides concrete token consumers. Inspect the cascade and states too: a later navigation rule may change height, selection and typography; extracting only the first declaration or only `:root` does not reproduce the component.

A palette extracted from an image or generated by a tool still needs mapping to roles and states. Use the matrix and acceptance criteria in [color refinement](color-refinement.md) before promoting candidates to tokens. Preserve automatic intent versus explicit choice, mode-specific aliases and value provenance; exporting hex values does not preserve these contracts by itself.

## Completed direction and spacing example

**Surface:** service settings. **Mode:** operation. **Direction:** calm, with text and grouping as hierarchy, without a hero. Existing typeface; body text at 1rem/line height 1.5 as a starting point; form up to 40rem and full available width on narrow screens; start alignment; semantic messages; primary action at the end.

**CSS example:** label to field 8 px; field to help 4 px; related fields 16 px; groups 32 px; panel padding 24 px. Help belongs to the field, fields belong to the group, and groups distinguish decisions. For compact density, experiment with 6/4/12/24/16 while preserving interaction and reading. Do not import these numbers blindly into an existing brand or native platform.

**Acceptance:** a two-line label does not overlap its field; errors grow in flow; long translations are not clipped; narrow widths preserve the task and margins.

```css
:root {
  --space-field-label: .5rem;
  --space-field-help: .25rem;
  --space-fields: 1rem;
  --space-groups: 2rem;
}
.settings-form { inline-size: 100%; max-inline-size: 40rem; }
.field { display: grid; gap: var(--space-field-label); }
.field-help { margin: 0; }
.field-control-and-help { display: grid; gap: var(--space-field-help); }
.field-group { display: grid; gap: var(--space-fields); }
.field-group + .field-group { margin-block-start: var(--space-groups); }
```

CSS does not associate labels/inputs/help: implement the corresponding semantics. Logical properties help with RTL. This example explains relationships; it is not a complete form.

## Usable handoff

For a component: anatomy, tokens, variants, events, focus and errors. For a flow: states/transitions and API dependencies. For an asset: path, dimensions, format, purpose, provenance/license and variant. For a screen: narrow/wide behavior and extreme content.

The handoff may fit in the change description. Do not create redundant files if code and documentation already explain the decision. With the design source and code, map the component/variant/prop to its implementation and token without assuming synchronization.

Before reconciling design-source/code, declare authority by scope and revision. Record `role -> token/alias -> mode -> component/property -> consumer -> evidence`. Equal hex values do not prove binding: inspect IDs, aliases and resolved values in the relevant modes. Preserve valid instances and overrides; a name/ID change requires checking consumers. If authority cannot be inferred and the choice changes identity, obtain that decision before the dependent mutation.

Deliver editability and format-specific losses according to [artifacts](artifact-workflows.md). An image of a component in a design editor or a chart in PPTX is not an editable component/chart.

## Evolution

Classify a change as an alias without effects, visual, behavioral or a contract break. Identify consumers; deprecate with a replacement and migration. Do not treat an old screenshot as normative if the product changed intentionally; record the version and reason for the new reference.
