# Reuse by capability, in the destination's identity

Use saved patterns whenever they solve the current task, without requiring the user to name their source project. This applies to every Forma pattern and to future authorized additions. Source names identify provenance or an explicit fidelity target; they are not activation passwords.

The agent performs this procedure after reading Forma. It is not model training, an automatic background process, or permission to modify other projects. A local correction stays local; do not add glass, a splash, a theme editor or 3D merely because a saved example contains it.

## Select before transferring

1. Inspect the destination's approved components, semantic tokens, typography, platform and task. Reuse what already solves the need.
2. Describe the missing capability in ordinary terms. Query the local catalog with a short capability phrase, for example `compact window`, `glass navigation`, `ink theme`, `articulated passport`, `product variants` or `pdf guide`. Run `node <forma-root>/scripts/references.mjs --query "..." --limit 3 --json` from the installed package; no source-project directory or brand name is needed. Portuguese terms such as `janela compacta`, `navegacao glass`, `gota de tinta` and `guia pdf` are supported by explicit aliases.
3. Read the selected card's `structure`, `adapt`, `avoid`, `verify`, evidence limits and linked contract. Multiple compatible patterns can contribute separate capabilities. Do not combine entire project identities. No match remains no match; do not invent a mechanism from an unrelated card.
4. Choose adaptation by default. Keep the mechanism's state, semantics and distinguishing behavior while binding its visual roles and content to the destination. Exact reproduction is a separate explicit request: freeze that source revision and the requested dimensions of fidelity instead.
5. Integrate only the needed mechanism in the existing stack, then verify the destination. A contract needs implementation; a specimen needs integration; a saved source's tests do not certify either one.

Search is lexical PT/EN lookup, not a semantic ranking of quality. For a long request, extract its capability phrase and retain the remaining constraints in the shared brief. External `--sites` and `--portfolios` searches still match identities only; this procedure does not convert historical candidates into observed mechanisms.

## Bind roles, never copy identity by accident

| Role | Resolve from the destination | Preserve from the mechanism |
|---|---|---|
| Accent, selected icon and marker | Approved accent with sufficient contrast on the actual navigation surface | Shared selection meaning, visible at rest, plus shape/semantics |
| Background, sidebar, pane and controls | Existing light/dark surface roles and transparency policy | Layer ownership, readable foreground, stable interaction |
| Text, muted text, focus and status | Destination foreground/focus/status roles in each supported mode | Readability, focus visibility and non-color status cues |
| Typography, density and radius | Existing font stack, content metrics, spacing and shape scale | Hierarchy, touch/keyboard access and reachable content |
| Logo, illustrations, photos and copy | Authorized destination assets, language and terminology | Structural slots, reading order and honest action boundaries |
| Routing, roles, data and persistence | Real destination owners, permissions and APIs | State transitions, cancellation, error recovery and lifecycle |
| Motion and material | Requested intensity, device budget, reduced-motion/transparency preferences | Interruption safety, fallback, cleanup and continuity |

Resolve each role for light and dark independently. Do not mechanically replace every source orange with the brand hex: an accent that works on white may fail on dark glass. Derive an accessible role variant when needed and document it in the destination's existing token system. Keep primary-action, selection and status colors distinct when the destination does. Consumer black, orange, yellow, green, fonts, radii and breakpoints are example values, not universal defaults.

For scoped assets, override their documented tokens on the component root; do not create global selectors or rewrite every consumer. Examples of existing integration boundaries:

- Clean shell: `.dc-shell` / `--dc-*`; bind accent, foregrounds, surfaces, font and shape to existing project variables in both modes.
- Soft Glass: `.forma-soft-glass` / `--sg-*`; its full landing uses `.forma-soft-glass-landing` / `--sgl-*`. Workspace and marketing surfaces have different owners.
- Ink theme: `mountInkTheme({ initialTheme, applyTheme })`; the host applies its palette, labels and persistence. The controller chooses no colors or font.
- Appearance editor: draft/commit/cancel adapters and contextual targets, with destination persistence. A frozen compact-editor profile applies only to requested fidelity.
- Book, passport and graph: use documented inputs, content/asset slots and lifecycle. Do not invent an arbitrary color override for a preserved renderer; inspect its public contract, adapt the supported material inputs or implement a scoped extension and verify it.

Example: a blue financial workspace and a warm editorial workspace may share the same compact scroll ownership and interruption-safe theme reveal. Each keeps its own surfaces, font, accent, labels and data. A green campaign may reuse the split landing composition without acquiring the source's telephony copy or yellow field.

The catalog is the searchable owner; this table connects families, not a second registry. Every packaged reference profile has a catalog resource path, including dated source profiles. The public catalog links authorized reusable material. Private kits, historic validation records, and source-specific measured values retain their original identity and do not become destination defaults.

## Save the next pattern the same way

When authorized to maintain Forma, use the [experience template](templates.md#reusable-experience): generic task/name -> invariants -> destination bindings -> contraindications -> available implementation -> evidence -> destination test. Put the source project's name and revision in provenance, not in the only route to the pattern. Reuse an existing card unless a distinct capability needs its own entry. Preserve stable IDs and links, and record superseded choices without promoting them as current defaults.

Add generic positive retrieval cases, an unsupported query, and a destination identity check. Register every new profile through the appropriate card. Keep unlicensed/private assets out of the distributed package. Saving the source alone is incomplete if no generic route reaches it.

## Verify the transfer, not just the lookup

Check that the distinguishing operation still works; colors, typography and assets belong to the destination; original product names/sample data did not leak; light/dark, keyboard, short/narrow layouts and reduced-motion behavior remain usable. Preserve permission and persistence boundaries. Test stale/rapid input where relevant.

Report separately: catalog discovery, available code, destination integration, runtime/rendered review and production. A brand-independent search test proves retrieval, not successful adaptation in every future project. A new destination requires its own verification; no old approval or test count is inherited.
