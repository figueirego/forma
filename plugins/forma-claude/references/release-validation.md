# Release validation with bounded evidence

Use this procedure when evaluating a skill revision, a portable capability, or completed design outputs. It defines a repeatable investigation, not current audit results, universal reliability, or release authorization. For ordinary interface corrections, keep the smaller [rendered validation loop](rendered-validation.md#minimum-execution-contract). The [evaluation scenarios](../evals/release-validation.md) test this protocol's decisions.

## Freeze the question before execution

1. Record the exact brief, allowed tools, initial consumer fixture, acceptance criteria, and intended platforms/states. Define whether the question concerns routing, a completed design, comparative improvement, component reuse, or retrieval. These require different evidence.
2. Freeze the skill files, dependencies/lockfile when relevant, and fixture. Record version and source revision plus a SHA256 manifest of the actual files supplied. Hash the exact UTF-8 brief and protocol bytes; a version label or commit alone does not identify uncommitted changes or the installed package.
3. Choose the trials and review method before starting. Give independent fresh contexts identical inputs and access. Do not supply another trial's output, reviewer feedback, solution, or expected evaluation answer. Self-checks are allowed and recorded. If a context inherits earlier work, disclose that limit rather than calling it fresh.
4. Each trial submits its complete output, consulted resources, tests, and limitations, then freezes a separate output manifest. Record submission time and manifest hash. Keep later review evidence outside that frozen directory. A trial with missing output remains incomplete.
5. Review only after submission, using the agreed criteria and the actual submitted files. Preserve the failed original and its findings. Put authorized corrections in a separate revision/directory with their own manifest and retest record; a correction after feedback is not another independent trial.

For example, two agents may independently build the same fictional editorial workspace with filters, completion/undo, and saved themes. Freeze content, storage semantics, viewport targets, and acceptance before they start. This is an example fixture, not a claim that either implementation passed. Follow the existing [version-comparison contract](../evals/routing-scenarios.md#compare-versions-without-confusing-evidence) for baseline/candidate comparisons and held-out variants.

## Browser proof matrix

Select rows relevant to the declared capability. Record **pass, fail, unverified, or not applicable with a reason** for each required context; an unavailable environment is unverified. Capture actual conditions, not only requested tool settings.

| Dimension | Record and exercise | Limit on the conclusion |
| --- | --- | --- |
| Loaded artifact | Local hashes, served responses, and loaded CSS/JS identity; include imported modules and affected overrides | A shared version marker or passing local test does not prove the open tab loaded those bytes. Preserve unsaved work before reload. |
| Layout | Requested viewport; actual CSS `clientWidth`/`clientHeight`, visual viewport when relevant, zoom, DPR, scroll extents, and critical element boxes; inspect visible and full-page captures | A requested 390px viewport is not proof of 390 CSS px. A long screenshot alone does not establish focus or reachability. |
| Browser diversity | Browser shell/version, rendering engine/version when available, OS, and environment type | Two shells using Chromium are not two independent rendering engines. An unknown engine remains unknown. |
| Input | Report `hover`, `pointer`, and relevant `any-*` media values; execute keyboard, mouse/fine pointer, and touch sequences separately | Narrow resizing does not produce touch input. Emulated touch is not a physical device or its virtual keyboard. |
| Accessible names | Inspect computed accessible names in the browser, especially inputs presented with an icon or placeholder; confirm each name identifies its task | A decorative icon, placeholder, or `aria-describedby` description does not replace an explicit label. Source markup alone does not establish the computed name. |
| Motion preference | With the page open, change `prefers-reduced-motion` through a supported OS setting or declared emulation; observe existing and newly triggered CSS/JS/canvas effects, interruptions, and return | A stylesheet rule or changing an app class does not prove a live media-query response. Name an emulated preference as emulation. |
| Visible content | Observe essential text, controls, images, and state before/during/after reduced motion, hidden/show, resizing, and the agreed no-JS/failure fallback | Stopping an animation while its content remains invisible is a failure. Declared DOM text is not visible-render proof. |
| WebGL path | Record context creation, actual renderer mode, unmasked WebGL vendor/renderer when the debug information is exposed, and a visible rendered object with its distinguishing interaction | Report unavailable/masked diagnostics explicitly. A renderer string is not GPU-utilization proof; software rendering is not hardware rendering. Geometry/unit tests, dependencies, or an empty canvas prove neither. |
| Runtime cost | State instrument, sampling interval, scene/state, foreground/hidden status, and units. Report frame cadence/FPS, CPU/process work, and GPU time/utilization/memory as separate measurements | RAF cadence is not GPU timing; low CPU is not low GPU cost. Without an appropriate GPU measurement, GPU cost remains unverified. Record profiler overhead and background throttling where relevant. |

Use [execution identity](rendered-validation.md#applying-110-to-pauta---scope-adaptation-and-execution-identity), [motion engineering](motion.md#engineering), and [verifier coverage](verification.md#verifier-coverage-and-receipts) for the underlying contracts. Supported WebGL rendering, a functioning static fallback, visual fidelity, and hardware performance are separate gates. Do not disable privacy controls or change graphics flags merely to obtain a preferred renderer label.

## Prove reuse in the consumer

Follow [consumer reuse](playbooks.md#h-reuse-capabilities-in-another-project) and the [platform adapter recipes](platform-adapters.md#verification-recipes-by-stack). Establish `contract -> actual import/adapter -> owner of state -> distinguishing operation -> rendered evidence` in the destination, preserving its stack and data.

- **Adapter and lifecycle:** mount, update data, unmount, remount, and repeat. Confirm subscriptions, timers, observers, contexts, and RAF work do not accumulate. Test cancellation during asynchronous initialization and updates while hidden. A standalone demo is not proof of a framework adapter.
- **Save and Cancel:** distinguish confirmed state, draft, preview, immediate preferences, and independent commands. Exercise real save -> immediate reopen -> reload, rejected storage -> retained draft -> retry, and cancel -> reopen. Inspect dirty state after successful acknowledgement, including first-use defaults, added entries and reset; serialization order must not create a false edit. Confirm one section's save does not commit another section's draft. Use the [settings state model](settings-modes.md#state-model).
- **Fallback and return:** force the relevant unavailable capability through a documented test path; verify honest mode reporting and usable content. Navigate away and back; distinguish full reload from a restored back-forward cache entry. Where BFCache is exercised, record `pageshow.persisted` and test resumed controls/observers without duplicate work or a permanently destroyed renderer. No cache restoration observed means BFCache remains unverified.
- **Framing and extremes:** test actual consumer containers, short windows, narrow panels, open/closed object envelopes, long unbroken names, empty data, large counts, and supported numeric limits. At input boundaries also test nonfinite/out-of-range values according to the contract. Observe clipping, overlap, reachable controls, focus, and resize recovery; a bounding-box formula alone is not visual approval.

For an interactive material object, rotate or otherwise exercise the requested volume, inspect the visible result, then test its static fallback independently. For a profile form, cancel a draft while keeping an immediately saved theme if that is its declared contract. Do not invent APIs or assume those examples are supported by every component. Refer to [object lifecycle](reusable-objects.md#cost-and-lifecycle) and [editing/storage cases](rendered-validation.md#minimum-editing-and-storage-cases) for detailed coverage.

## Prove reference retrieval separately

Keep `candidate identity -> bounded observed feature -> supported query result -> destination decision` distinct. A source's date, original/resolved URL and ID, conditions, evidence assertion, status, caveats, and rights accompany each claim. Observing one control does not promote every property of its site.

To demonstrate selection during creation, retain the exact machine query and response bytes, the source-index revision, the selected claim IDs, the reason for adaptation, and destination selectors. After submission, replay the queries against that frozen index and test the resulting destination behavior independently. Include at least one unsupported query and its explicit abstention. An agent selecting observations through a deterministic lookup demonstrates that bounded workflow; it does not prove automatic visual understanding or feature coverage of every catalog candidate. A text-only source refresh does not refresh an earlier interaction observation.

For [observed-experience search](reference-library.md#search-observed-experiences), define expected positive and negative queries before adjusting labels. Test the exact feature/use case, an unrelated term, a term found only in an unverified limit, incompatible terms from different claims, and an unknown filter. The result must identify the supporting observed claim; unsupported queries must return no match or an explicit invalid-filter error, without candidate/guide fallback. Validate source sections/assertions and preserve existing identity-only lookup. Schema and source-note checks do not authenticate the underlying observation; revisit time-sensitive sources. Follow [experience evidence states](experience-library.md#states-and-evidence).

## Report the scope actually established

For every trial and consumer, connect criterion -> method/environment -> artifact revision -> observed result -> evidence path -> remaining limitation. Preserve incomplete and failed gates rather than hiding them inside an average. Package integrity, routing, retrieval, rendered task success, fidelity, and runtime cost remain separate results.

A two-trial report states the outcomes of those two original outputs, then any separately reviewed corrections. Even if both satisfy a criterion, that bounded sample does not establish population reliability, universal design quality, user preference, or other browsers/devices. Without an equivalent executed baseline, do not claim improvement. Use [evidence records](verification.md#verifiable-local-record) for structure, and read their stated coverage before treating a checker's exit code as acceptance. This procedure introduces no mandatory trial count, paid runner, deployment, or publication step.
